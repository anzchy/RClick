# Finder UI driver: the safety contract on one page

Every `ui.sh` / `calibrate.sh` entry point that acts on the desktop, and the checks it makes before it acts. A failed
check exits **65** (refused: nothing was done, an open menu was closed) or **70** (environment), never a guess.
Code: `scripts/finderdrive.py` (side effects), `scripts/finderui.py` (the pure checks, unit-tested),
`scripts/axprobe.swift` (AX), `scripts/calibration.py`. The pitfalls behind each check are in
[ui-driver-notes.md](ui-driver-notes.md).

## Checks every acting command shares

| Check | Where | What it requires |
|---|---|---|
| GUI lock (Python) | `finderdrive.require_lock` → `finderui.check_lock` | `gui-lock.sh status` shows ONE complete owner record (`HELD:` plus the eight fields of `gui-lock.sh`, each once) with `project=rclick`, `batch=$RCLICK_GUI_LOCK_BATCH` and `acquisition_id=$RCLICK_GUI_LOCK_ACQUISITION_ID` (exported after `gui-lock.sh acquire`). Else 70. The record's `pid` is the short-lived acquire process (gui-lock.sh protocol), so pid liveness is not checked: the acquisition id identifies this run's lock. |
| GUI lock (axprobe) | `axprobe.swift` `requireLock()` in `act` and `menu-session` | the same check, run again by the AX helper itself (`python3 <driver> lock-check`), so calling `axprobe` directly does not skip it. |
| AX helper integrity | `finderdrive.probe_binary` | `axprobe` is compiled into `~/Library/Caches/rclick-axprobe/<digest>/` (every path from the home directory down is `lstat`-checked one level at a time, nothing is created or read below a refused one: home, `~/Library` and `~/Library/Caches` must be real directories of this user that group and other cannot write; `rclick-axprobe/` and `<digest>/` real 0700 directories of this user; the executable a regular file of this user that group and other cannot write. A symlink at any of these levels is refused, not followed. Above the home directory nothing is checked), built in a private temporary directory and renamed into place. |
| Modifier state (fail closed) | `finderdrive.require_clean_input` → `modifiers.sh state`, `finderui.held_modifiers`; `modifiers.sh check` in `rightclick.sh` and `click.sh` | `choose` and `open-menu` (before anything is selected, and again right before each right-click), `press-button` and `grant`, and the raw `rightclick.sh` and `click.sh` before they post anything, read the modifier state: `CGEventSourceFlagsState` of the HID system state and of the combined session state, and their union (a read: no event posted). The union, because the extension takes Option as held when either state has it (`FinderSyncExt.swift` `isOptionKeyPressed`). Shift, Control, Option or Command held → 65 naming the key and the flags, nothing selected, clicked, posted or pressed; an unreadable state → 70. A stuck Option turns every Delete Direct into its skip-confirmation form (device run, 2026-11-18). |
| Modifier release | `finderdrive.pressing`, `rightclick.sh`, `modifiers.sh release` | the only modifier the driver posts is Option (`--option`), and a release clears only what was pressed: the Option key-ups and a flagsChanged event whose flags are the HID state minus Option (never all-zero flags, which would also clear a key someone else holds, or Caps Lock). `rightclick.sh … option` holds Option 1 s after the click (the extension reads it once, while the menu is built), then releases it in a JXA `finally`; its osascript runs in the background and the shell releases again however it ended (a SIGTERM or SIGKILL of osascript skips the `finally`) and on the shell's own INT/TERM/HUP (it stops osascript first; exit 130/143/129), reads the state back, keeps the failure status and never prints `released` when Option is still set (a clean click whose release fails → 70). `finderdrive` releases it once more after `rightclick.sh` returns, on success and on every failure, Ctrl-C (exit 130) and SIGTERM (exit 143), and reads the state back: Option still set → 70; a release that fails under Ctrl-C or SIGTERM is reported (`the cleanup did not finish: …`), not claimed. `key.sh`, `kc.sh` and `finder-kc.sh` pass modifiers to System Events (`using {… down}`), which releases them itself; the check before the next click catches one that stays. |
| Path identity | `finderui.clean_path`, `parse_selection` | paths compare exactly: whitespace and case are significant, both sides NFC, one trailing `/` dropped; a path with a line break is refused. The selection is read back with a count line, so a lost or split line is refused. |

## Entry points

| Entry point | Acts on | Checks before acting |
|---|---|---|
| `ui.sh select PATH...` | Finder selection (AppleScript) | lock; reads the selection back and compares it exactly with the paths (65 on a difference). |
| `ui.sh open-menu NAME [--option]` | right-click on a row (leaves the menu open, for reading) | lock; brings Finder to the front through System Events; the one visible row named exactly NAME (duplicates refused); `AXSelected` through `axprobe act` (lock, role and title re-checked at the element); rows re-read and the row must not have moved; the menu is polled for up to 4 s at the point, else 65 naming what the probe found; any failure after the click closes the menu it opened (as for `choose`), so a failed opener leaves no menu behind. No AppleScript to Finder after the click. |
| `ui.sh open-menu --background [--option]` | right-click on the window background (leaves the menu open) | lock; deselects, then reads the selection back: it must be empty; `finderui.background_point`: the front window's one file list (not the sidebar), at least 30 pt of empty space below its rows, inside its scroll area; the menu is polled as above. |
| `ui.sh close-menu X,Y` | `AXCancel` on the menu (`axprobe menu-cancel`), then Esc to Finder | lock; reads the menu at X,Y through AX: none → nothing sent; the menu must be Finder's (`menu-cancel` compares the owner pid, 65 otherwise, nothing sent); Esc (System Events, key code 53 to process Finder) only while AX still shows that menu; 70 if it is still open afterwards. No AppleScript to Finder. Use it instead of `finder-kc.sh 53`. |
| `ui.sh choose TITLE [--sub ITEM] [--option] --group ... (--target PATH... \| --background DIR)` | selects (AppleScript), right-clicks, `AXPress` on RClick's item | lock; ONE process, and every AppleScript call to Finder happens BEFORE the right-click (with a Finder menu open they time out: device run, 2026-11-18). Before the click, through AX (`finderui.target_row`): every target's row is the one visible row with its name and carries the target's full path as `AXURL`; the rows marked selected are exactly the targets; the row has not moved between two reads. `--background DIR` (`finderui.front_folder`): no row selected and every row's `AXURL` parent is DIR; an empty folder has no rows and is refused (65), never guessed. After the click the menu is polled for up to 4 s; ONE `axprobe menu-session` process then holds it: its owner pid must be Finder's; the Compress title names the target (`Compress N Items` for N; none for `--background`); TITLE must be in RClick's group, the ONE exact run of the `--group` titles (at least two, the full configured run; fewer is a usage error, 64) after the last `Quick Actions` (none or two runs refused); then, with the menu still open and held, the front Finder window is read AGAIN through AX (`finderui.bound_menu`, no AppleScript): the selected rows' `AXURL` set must still be the target set, every target the one visible row of its name with its full path, and the clicked row still at the click point (`--background`: the front folder still DIR, nothing selected), because the Compress title proves only a basename or a count; if that read fails or disagrees: 65, nothing pressed; axprobe then re-checks, on the menu it holds, the owner pid, every top-level title, the item title and the submenu item title (before and after opening the submenu) before `AXPress`. From the right-click on, any refusal or failure (an AX or transport error, a session that cannot start, an abort that times out) presses nothing, ends the session and closes the menu that click opened (`AXCancel`, then Esc to Finder; a cleanup that fails is named beside the original error, which keeps its exit code). Every `AXCancel` in axprobe first checks that Finder (the session's owner argument) owns the menu: a menu of another process is abandoned and left open. |
| `ui.sh press-button PID TITLE` | `AXPress` on a button | lock; PID must be Finder, RClick's FinderSyncExt (by executable path), the RClick of this run (`$RUN_DIR/rclick.pid`, RClick executable) or a calibration `osascript`: never a system prompt; exactly one button with that title (in the window holding `--window-text`); `axprobe act` re-checks role and title. |
| `ui.sh grant PID FOLDER` | selects a panel entry (row mode), presses its button | **Distrusted** (device run, 2026-11-18; a follow-up issue tracks it): on the `osascript choose folder` panel, row mode failed `axprobe: select failed: AXError -25205` (`AXSelected` on the entry's `AXGroup`) and current-folder mode `axprobe: press failed: AXError -25204` (`AXPress` on the button); nothing was selected or pressed. Use `ui.sh press-button <rclick pid> "Grant Access"` on RClick's panel when it opens at the folder to grant (it worked on that run). The checks below still apply: lock; the same PID allow-list; the panel is matched by full paths, never by a basename. Column view (the real panel; `finderui.browser_columns`): every entry carries `AXURL`, each column lists one folder and an entry of the column before it, no column is empty, the `Where:` pop-up names the deepest folder (or, after a select, its parent); the target is the deepest column's folder (current mode: no entry there marked selected) or an entry of it (row mode: `AXSelected` on its `AXGroup`). List view (rows, ASSUMED): each row's `AXURL`, the location from the rows. After selecting, the panel is re-read (`finderui.panel_ready`): column view, the browser must now show the target; list view, the target is the only selected row; same window and button; else nothing is pressed. The panel must close afterwards. |
| `ui.sh lock-check` | nothing | the lock check alone (axprobe calls it). |
| `rightclick.sh X Y [option]`, `click.sh X Y` (raw) | a synthetic click at a point (the sidebar recipe; `ui.sh` calls `rightclick.sh` itself) | the modifier state only (no lock, no element check): a held modifier → 65, unreadable → 70, nothing posted. With `option` it releases only the Option it pressed, on every path (Modifier release above). Read the menu with `ui.sh menu` and press through `ui.sh` commands, not with another raw click. |
| `calibrate.sh RUN_DIR --group ... --background-group ...` | a throwaway Finder window, one alert, two folder panels, the pasteboard | lock; the modifier state is clean at the start (`modifiers-start`, else 70 before the fixture is made), right after `option-menu` (`modifiers-after-option`) and at the end (`modifiers-end`): 21 steps; the fixture folder is allocated exclusively (`mkdtemp` under `$RUN_DIR/fixtures/`, files `O_EXCL|O_NOFOLLOW`) and cleanup removes only what this calibration created or adopted. Teardown (stop its osascripts, close every menu a step opened with `close-menu`, close the fixture window by the Finder window id read when it opened, remove the fixture) runs on every path, including a failed step and Ctrl-C: a failing call (an osascript timeout, a missing tool) becomes a `note:` line and never skips the later calls, and the PASS/FAIL report plus the notes is always printed and saved; it terminates only the `osascript` processes it started; the menu steps run the `ui.sh` command lines above as subprocesses. `--dry-run` touches nothing. |

## Not covered offline, and not by calibration

- The axprobe re-check before `AXPress` (`menu-session`) and its lock check are compiled and type-checked by the unit
  tests when `xcrun` exists; their behaviour on a live menu is proven only by a device run (`calibrate.sh`).
- That the 1 s Option hold of `rightclick.sh` is long enough for the extension to read Option while Finder builds
  the menu, and that the release events clear the HID state: calibration's `option-menu` and
  `modifiers-after-option` prove both on the device.
- SIGKILL of the whole process tree (`ui.sh`, `rightclick.sh` and its osascript together) during an Option click,
  and a second signal while a release is running, cannot be handled: Option may stay set. Nothing records it, and
  nothing has to: the next acting `ui.sh` command or raw click reads the live state and refuses (65), and the next
  calibration fails at `modifiers-start` (70, before the fixture). Clear it as the refusal says.
- RClick's own sandboxed folder panel as a `grant` target: calibration uses an `osascript choose folder` panel.
  PERM-01 on the device proves RClick's panel.
