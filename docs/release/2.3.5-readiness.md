## Identity and version findings

Workflow IDs (lines 21–25), project bundle IDs and all three entitlement files agree on `cn.anzchy.RClick`, `cn.anzchy.RClick.FinderSyncExt` and `group.cn.anzchy.RClick`. The Debug entitlements also exist and currently match the app Release entitlements. No old bundle ID or upstream release URL remains in the workflow. Project `DEVELOPMENT_TEAM = GRT84NAK4T` remains: owner must establish whether it is their team; the manual release signing uses `APPLE_TEAM_ID`, but local signed builds still use the project value.

App and extension Debug/Release marketing versions are now 2.3.5. Test bundle marketing versions remain 1.0. Extension Info.plist is generated with the target marketing version as CFBundleShortVersionString. The extension should ship at the app's marketing version; no application code compares app and extension marketing versions. `SingleInstanceGuard` compares **app copies** using CFBundleShortVersionString and chooses the higher version, then later launch, then lower PID. It bypasses termination for hosted tests. This does not enforce extension agreement.

`RClickApp.swift:39–41` constructs UpdateManager from the app short version. `Updater.swift:152–156` reads the fork releases list; drafts are excluded, prereleases included, highest version wins. Installation checks the staged **app** short version equals the expected release version (`Updater.swift:465–466`), not the extension version. Test-host app builds use 2.3.5; the separate test bundle's 1.0 does not affect that check. Local 2.3.5 builds will not offer an equal-version release as a newer update.

Release workflow lines 175–187 override `CURRENT_PROJECT_VERSION` with `date +%Y%m%d%H%M` and `MARKETING_VERSION` with the tag after stripping `v`, across built targets. Thus a numeric v2.3.5 gives release app/extension short version 2.3.5 even without a project bump; project values govern ordinary local builds. This also overrides the test target when built under those command-line settings, though the release command does not run tests. The four app/extension project build numbers stay **20261114001**; test build numbers stay 1. No project build-number bump is required to produce a timestamped workflow artifact; the owner decides whether local-build numbering should also advance.

1. **Release blocker — #40 / signing NOT VERIFIED.** `Shared/IPCKeyProvider.swift` queries Keychain service `cn.anzchy.RClick.ipc.v2`, account `installation-key`, using the App Group identifier as `kSecAttrAccessGroup`. The tracked entitlements declare the App Group but no explicit `keychain-access-groups`; the signing step adds only application/team identifiers. Source agreement alone cannot prove that the released profiles authorize this access group on a clean Mac. Run #40 before publication; capture exact OSStatus. If denied, owner must establish the correct profile/entitlement authorization before any separately reviewed diff. The 0600 container-file fallback is an owner decision, not enabled here.
2. **Release blocker — final device validation #12 and release artifact installation remain PENDING.** Unit tests do not prove Finder behavior or sandbox grants. Fill the notes table with public evidence and update the ledger/metrics on the release head.
3. **High operational risk — automatic tag deletion**, `release.yml:421–427`. Any failing step can delete v2.3.5, including after packaging or partial release creation. Proposed separately reviewed diff: remove the Cleanup Tag on Failure step; retain a failed tag/run for diagnosis, with explicit owner-controlled recovery. Do not push a production tag expecting a harmless dry run.
4. **Publication policy — prerelease is offered to users**, `release.yml:416`, `Updater.swift:152–156`. Default for this draft: preserve the existing prerelease flag; numeric v2.3.5 is still offered to older installs. Owner must decide whether a stable release is wanted; if yes proposed diff is `prerelease: true` → `prerelease: false` in a separately authorized workflow change. The current flag does not withhold updates.
5. **Draft notes are not wired into publication**, `release.yml:415`. It generates notes rather than loading this draft. Proposed diff after pending rows/date are finalized: add `body_path: docs/release/2.3.5-notes.md` under Create Release `with:` (decide whether to retain generated notes). Owner/delegator must ensure the reviewed notes reach the release.
6. **Reproducibility/coverage**: floating macos-latest/latest-Xcode and Homebrew create-dmg are unpinned; output is arm64 only. `v*` also permits nonnumeric suffixes, while Version.compare does not implement SemVer prerelease ordering. Proposed separate hardening: validate extracted VERSION against `^[0-9]+\.[0-9]+\.[0-9]+$` before build. For this release push exactly v2.3.5. No Intel compatibility claim is made.

## Version agreement check

No existing app/extension version-agreement assertion was found. This small repository check covers both configurations without changing Swift or agent tooling. Run at the repo root; a differing target value fails the assertion. Hosted test bundle 1.0 remains intentional.

```sh
python3 - <<'PY'
import plistlib, subprocess
project = plistlib.loads(subprocess.check_output(['plutil', '-convert', 'xml1', '-o', '-', 'RClick.xcodeproj/project.pbxproj']))['objects']
versions = {}
for target in project.values():
    if target.get('isa') == 'PBXNativeTarget' and target.get('name') in ('RClick', 'FinderSyncExt'):
        configs = project[target['buildConfigurationList']]['buildConfigurations']
        versions[target['name']] = {project[c]['name']: project[c]['buildSettings']['MARKETING_VERSION'] for c in configs}
assert versions == {name: {'Debug': '2.3.5', 'Release': '2.3.5'} for name in ('RClick', 'FinderSyncExt')}, versions
print('PASS app/extension Debug/Release versions agree at 2.3.5')
PY
```

The last documented release section stays 2.3.1; the consolidated section retains changes from that documentation baseline, including inherited changes already present by v2.3.4.
